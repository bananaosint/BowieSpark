FIT & Club Scheduling Platform — Build Sheet
Project: A student self-scheduling system for FIT (Flexible Instruction Time) and club signups, modeled on Enriching Students, built for a ~3,000-student AISD high school.
Status: Pre-build / v1 spec locked. Fake data during beta. District engagement to run in parallel with development.

3. V1 Feature Set
Student flow
Log in with school email (@stu.austinisd.org only) — either email/password or Google OAuth, both supported side by side
Homescreen: a weekly view — today's FIT plus the rest of the week, so students can plan/sign up in advance
If a day is teacher-overridden, that day shows only the assigned session (no alternate options), with a note pulled from the admin-editable PolicyText table (seeded default: "Teacher assigned — attendance is mandatory. Missing it results in an automatic referral.")
If a day is self-selected or open, the student sees their current pick (if any) and can browse/change it
View sessions organized into subject tabs: Math, Science, English, LOTEs, Fine Arts, Electives, plus an "Other" catch-all for anything that doesn't fit — this starting list is admin-editable so tabs can be added/renamed later
Scroll within a tab to browse sessions
Self-schedule into any open, non-full session
Change selection freely until the admin-configured cutoff (default: right up to the bell; admins can push it back, e.g. "must lock in by 9pm the night before")
If a teacher has issued an override, that assignment is shown as locked and cannot be changed by the student
View current + past schedule
Teacher flow
Create session form fields:
Title (free text, e.g. "Cowlin's Cosmic Study Lab", "FILM CLUB!!")
Capacity limit (integer)
Recurrence: daily, or specific days (e.g. Fridays only, Mon–Thu)
Description (50-word max, enforced in UI)
Prerequisites (free text, e.g. "Must be enrolled in Band") — display-only, not enforced by the system; students see it but aren't blocked from signing up
Override tool: assign a specific student (or list of students) into a session; this assignment always takes priority over the student's own choice and cannot be undone by the student
Take attendance per session: Present / Tardy / Absent / Cut
View/manage roster and pending requests for their own sessions
Admin flow
Full visibility across all sessions/teachers/students (fake data in v1)
Set the org-wide (or per-session) signup lock-in cutoff
Analytics dashboard: usage by department/session, no-show trends, students who repeatedly fail to schedule (structure now, populate meaningfully once real data flows in v2)
Account management (manually add/remove test users in v1)

4. Data Model (v1, simplified)
User
 - id, email (@stu.austinisd.org / staff domain), role (student/teacher/admin), display_name

Session
 - id, title, teacher_id, description (≤50 words), capacity,
   recurrence_type (daily | specific_days), days[] , subject_tag_id,
   prerequisites (text, display-only), created_at

SubjectTag
 - id, name, sort_order
 - Seeded with: Math, Science, English, LOTEs, Fine Arts, Electives, Other
 - Admin-editable (add/rename/reorder) — not a hardcoded enum

Enrollment
 - id, session_id, student_id, status (self_selected | teacher_override),
   date, locked (bool)

Attendance
 - id, enrollment_id, date, status (present | tardy | absent | cut)

CutoffConfig
 - scope (global | per_session), cutoff_rule (e.g. "T-0" bell-time, "T-1 day 9pm"), set_by_admin_id

PolicyText
 - key (e.g. "teacher_override_notice"), value (admin-editable string)
 - Seeded default for teacher_override_notice: "Teacher assigned — attendance is mandatory. Missing it results in an automatic referral."

No real student PII (grades, IEP/504, discipline, SIS IDs) goes anywhere near v1 — everything is seeded fake data.

5. Tech Stack
Frontend: React (Vite) — a standalone SPA rather than a full-stack framework
Backend: Node.js + Express, as a separate API — confirmed, keeps the whole stack in JavaScript
ORM: Prisma — works the same way against Express, and has first-class SQLite support
Auth: Auth.js's core library supports Express directly (not just Next.js), so the domain-gated email/password + Google OAuth plan still holds
Hosting: A Linode VPS running both pieces — the React build served as static files via nginx, and the Express API kept alive with a process manager (pm2 or a systemd service). A proper datacenter box means a stable IP, real uptime, and the ability to configure firewalling and patching the way a district IT review would expect to see.
Still to set up on the VPS: nginx as reverse proxy, TLS via Let's Encrypt (free, auto-renewing), a firewall (ufw or Linode's Cloud Firewall), and a process manager for the Express app so it restarts on crash/reboot
Database: SQLite — a single file, which fits naturally with the single-VPS setup (no separate DB server to run, trivial to back up by copying the file, and Prisma treats it as a first-class option). One thing worth watching before the real v2 rollout: SQLite serializes writes (one writer at a time), which is fine for v1's fake-data beta and likely fine even at 3,000 students for normal usage, but worth load-testing the exact "everyone signs up the second the window opens" spike scenario before real students depend on it. If that ever becomes a bottleneck, migrating to Postgres later is a straightforward Prisma schema change rather than a rewrite.

6. Authentication Plan
v1: Email/password signup via Auth.js, gated to @stu.austinisd.org addresses only (validate domain server-side, not just client-side)
v1 stretch / v2: Google OAuth (also via Auth.js) — since AISD accounts are Google Workspace-backed, "Sign in with Google" restricted to the district domain gets you real identity verification without needing a formal SIS integration. Worth building this earlier rather than later since it removes password-management entirely.

7. Compliance & District Approval Checklist (for the v1 → v2 transition)
 Identify a sponsor inside AISD (counselor, instructional tech coordinator, or admin) to champion the tool internally
 Confirm AISD's ed-tech vetting process (many TX districts use a platform like LearnPlatform, or a direct IT/legal review)
 Prepare to sign whatever Data Privacy Agreement AISD requires (Texas SB 820 sets baseline requirements for ed-tech vendors serving public schools) before any real student data touches the system
 Confirm hosting meets whatever data-residency/security bar AISD sets (US-based, encrypted at rest and in transit)
 Scope what SIS data is actually requested (roster + schedule only, ideally — avoid ever requesting grades/IEP/discipline data unless a feature genuinely needs it)
 Get IT's read on whether Google OAuth restricted to the district domain satisfies their identity-verification bar, or whether they'll require full Clever/ClassLink SSO
